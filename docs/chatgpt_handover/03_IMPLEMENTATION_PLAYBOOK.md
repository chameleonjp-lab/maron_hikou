# 03. 実装プレイブック

## 1. 改修の原則

次の改修は、`index.html`を一度に全面書換えしない。ゲームループ、敵生成、成長、ランキングは互いに依存するため、**計測を先に置き、小さな変更を独立検証し、再現可能なseedを導入してから数値を調整する**順で進める。

> 優先順位は「プレイヤーの負けが理解できること」→「同条件の比較ができること」→「難易度を微調整できること」である。見た目、敵種、演出はこの順序を追い越さない。

## 2. タスクA — 初期攻撃力の下振れをなくす

### 目的

W5前に攻撃強化ゼロとなる確率を0%にし、ボス戦の合否を初期抽選だけで決めない。

### 最小変更案

`rollUpgrade()`で、初回レベルアップ（`level === 2`相当）だけ攻撃系候補から抽選する。攻撃系は`bullet`、`firerate`、`piercing`である。2回目以降は現行の候補全体からの抽選を維持してもよい。

```js
const ATTACK_UPGRADE_IDS = new Set(['bullet', 'firerate', 'piercing']);

function rollUpgrade() {
  let candidates = UPGRADES.filter((u) => gameState.upgradeCounts[u.id] < u.max);
  const isFirstUpgrade = gameState.level === 2;
  if (isFirstUpgrade) {
    const attacks = candidates.filter((u) => ATTACK_UPGRADE_IDS.has(u.id));
    if (attacks.length > 0) candidates = attacks;
  }
  // 以降は既存の抽選・適用処理を継続
}
```

### より良い変更案

毎回、攻撃・防御・回収/回避から1候補ずつ提示し、プレイヤーに1つ選ばせる。これにより「今回のビルドを自分で選んだ」という納得感が出る。モバイルでは選択画面中にゲームを停止し、3つの大きなボタンを縦配置する。

### 受け入れ基準

| 観点 | 合格条件 |
|---|---|
| 下振れ | 100,000試行でW5直前の攻撃強化ゼロが0件。 |
| 上限 | 強化上限に達した項目は候補に戻らない。 |
| UX | レベルアップ中に敵・弾・タイマーが動かず、選択が視認・操作できる。 |
| 既存機能 | Lv.12以後のスコア変換、結果表示、リトライで壊れない。 |

## 3. タスクB — 追従をフレーム独立化する

### 目的

30fps、60fps、120fpsで同じ指の操作がほぼ同じ時間で機体へ反映されるようにする。

### 実装場所

`updatePlayer(delta)`の現行補間を置換する。クランプ、ターゲット更新、発射ロジックはそのまま残す。

```js
const PLAYER_FOLLOW_LAMBDA = 25;

function updatePlayer(delta) {
  const alpha = 1 - Math.exp(-PLAYER_FOLLOW_LAMBDA * delta);
  player.x += (player.targetX - player.x) * alpha;
  player.y += (player.targetY - player.y) * alpha;
  clampPlayer();
  // 既存の自動射撃処理
}
```

`PLAYER_FOLLOW_LAMBDA`は最終値ではない。旧60fps時の体感へ近づける初期値として25を置き、実機で調整する。元の35%/frameは60fpsで約89msの90%追従に相当するため、初期値はおおむねこの感覚を目安にする。

### 受け入れ基準

| 模擬FPS | 90%追従時間 | 判定 |
|---:|---:|---|
| 30fps | 基準値±10% | 合格 |
| 60fps | 基準値±10% | 合格 |
| 120fps | 基準値±10% | 合格 |

加えて、canvasのスケール、`PLAYER_FOLLOW_OFFSET`、端クランプ、pointer capture、リタイアモーダル中の停止が変わらないことを確認する。

## 4. タスクC — 競技用の再現可能な乱数を導入する

### 目的

ランキング対象のプレイで、敵の出現位置・移動位相・ドロップ・強化候補を同条件にする。

### 設計方針

| 項目 | 推奨 |
|---|---|
| RNG | `Math.random()`の直呼びをやめ、seed付きPRNG関数へ集約する。 |
| seed | `date + gameVersion + mode` を入力として日次seedを作る。通常モードは任意seedまたはランダムseed。 |
| 記録 | `seed`、`rulesVersion`、`clientVersion`を結果・送信ペイロードに含める。 |
| モード | ランキング対象の「本日の飛行」と、ランダムな通常飛行を分離する。 |
| 再現テスト | 同seed・同入力列で、敵出現・ドロップ・強化が同じ順序になる。 |

### 実装の段階

1. `random()`ラッパーを追加し、内部は一旦`Math.random()`を返す。
2. 敵出現X、パターン、敵位相、ドロップ、戦利品種、強化抽選の全箇所をラッパーへ置換する。
3. xorshift32等の小さなseed付きPRNGを実装し、`resetGameState(seed)`で初期化する。
4. モードとseedをUI・結果・送信値へ通す。
5. 同seedの再現テストを追加する。

### 注意

ランダム値の呼び出し回数自体が再現性の一部になる。描画演出のための乱数とゲーム結果を決める乱数を混ぜない。演出用の粒子乱数は別PRNG、または結果に影響しない乱数に分離する。

## 5. タスクD — ボスTTKと敵密度を再調整する

### 目標

「適切に成長して回避できたプレイヤーが、長すぎず短すぎないボス戦を行う」状態を作る。推奨する計測下限は、全弾命中の理論TTKでW5が12〜20秒、W30が25〜40秒程度、P10〜P90の幅が20秒以下である。

### 調整の順序

1. **攻撃保証を先に入れる。** これなしにボスHPだけを触ると、下振れ対策ではなく中央値合わせになる。
2. **固定seedで測る。** ランダム100回の平均だけでなく、最悪寄りseedも確認する。
3. **基礎DPSまたはボスHPを一箇所ずつ調整する。** 弾数、連射、貫通、敵HP、敵数を同時に変えない。
4. **W5、W10、W20、W30で確認する。** W30だけ最適化しない。
5. **実プレイで回避中の実効命中率を測る。** 理論TTKは出発点であり完成判断ではない。

### 敵密度の扱い

現状は敵数を2倍にした一方、ドロップ率を半減して経験値期待値を据え置いている。敵の数を増やすなら、次のどちらかを選ぶ。

| 方針 | 何を固定するか | 向く体験 |
|---|---|---|
| 回避圧を上げる | 成長速度も少し上げ、敵密度増と報酬増を連動。 | 積極的に拾いに行く高密度シューティング。 |
| 読みやすさを優先 | 敵数を戻し、敵の役割・配置・弾幕の違いで難しくする。 | スマホで視認・回避しやすいシューティング。 |

「敵を増やすが報酬は増やさない」は、リスク/報酬設計として避ける。

## 6. タスクE — 逃走敵と弾幕上限を設計する

### 逃走敵

まず、逃走を許容するかを決める。撃破・回収を核に据えるなら、逃走数を`gameState`へ記録し、結果画面に出す。次に、逃走により失うものを明示する。たとえば逃走敵ごとに波突破ボーナスを減らす、あるいは「撃破率」をスコアへ反映する。

### 敵弾上限

既に発射された古い敵弾を削除する現行方式は、プレイヤーに見えない救済・不公平を生む。代わりに、発射時点で上限を超えないよう、次のどれかを行う。

- 画面内の敵弾数が高い間は、低優先度の敵の発射タイマーを遅延する。
- 敵種・ボスフェーズごとに弾数予算を持たせる。
- 弾速や寿命を調整して同時存在数を制限する。
- 高密度波では敵数を減らし、弾幕パターンの質で難しくする。

受け入れ基準は「上限に達しても、既に表示された弾が突然消えない」ことである。

## 7. タスクF — ランキングを信頼できるものにする

### クライアント側

- `scoreSent`による二重送信防止は維持する。
- 結果に`seed`、ルール版、クライアント版、モードを表示または記録する。
- 通常ランダムモードと正式ランキングを混ぜない。

### サーバー側（要Supabase側変更）

| 最低限 | 推奨 |
|---|---|
| `game_slug`固定検証、表示名長制限、進行度1〜31、表示スコア0〜9,999,999を検証。 | 日次seed照合、プレイ時間の妥当性、レート制限、同一プレイIDの重複拒否。 |
| 不正な値をRPCで拒否。 | 入力またはイベント要約を使ったサーバー再計算/異常検知。 |
| 送信元に関わらず同じ値域を強制。 | リプレイ可能な決定的ゲーム状態を保存。 |

> クライアントの公開可能キーを隠すことは解決策ではない。ブラウザゲームではクライアントを信頼しない前提でRPCを設計する。

## 8. 実装時の禁止事項

| 禁止 | 理由 |
|---|---|
| `index.html`を大規模に分割して別構成へ移す。 | 現行の公開・管理方針と衝突し、移植リスクを増やす。 |
| 乱数を演出とゲーム結果で共用したまま固定seed化する。 | 描画変更だけでランキングの再現性が壊れる。 |
| 適当な数値変更を複数同時に行う。 | 原因と結果が追えず、バランス調整が不可能になる。 |
| 生データ・再現スクリプトを更新せずに「改善した」と判断する。 | 監査可能性を失う。 |
| Supabaseの実RPCを確認せずにクライアントだけで安全性を宣言する。 | 不正送信の有無はサーバー実装で決まる。 |
