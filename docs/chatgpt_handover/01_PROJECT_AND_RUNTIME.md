# 01. プロジェクトと実行時アーキテクチャ

## 1. プロダクトの目的

マロン飛行は、スマホ縦持ちで遊ぶ1人用の2D縦スクロール飛行機シューティングである。プレイヤーは自動射撃を前提に、機体移動、敵弾回避、戦利品回収へ集中する。戦利品は経験値になり、レベルアップ時にはランダム強化が即時付与される。30ウェーブ目のボス撃破がクリア条件で、永続強化は持たない。

設計上の価値は、単純な「敵を倒す」ではなく、**敵を倒した地点へ近づいて戦利品を回収する危険**にある。安全な位置に留まると成長しにくく、回収に寄ると被弾しやすい。このリスクと成長の交換を保ったまま、運と端末性能による不公平を削ることが改修の中心課題となる。

## 2. リポジトリの制約

| 項目 | 現状・制約 | 引継ぎ上の注意 |
|---|---|---|
| 実装形式 | `index.html` 1ファイルにHTML/CSS/JavaScriptを同居。 | 分割は初回版の方針に反する。大規模修正は明確なセクション見出しを維持する。 |
| 外部素材 | 画像・音声・外部JSなし。CanvasとCSS・絵文字で表現。 | 画質改善を理由に外部画像へ依存しない。 |
| 主対象 | iPhone SE級の小さい縦画面。 | デスクトップで動くことだけでは合格にしない。 |
| 操作 | Pointer Events。指の70論理px上へ機体を追従。自動射撃。 | 追従式は改修優先。canvas座標変換とクランプを壊さない。 |
| 競技記録 | Supabase RPCへ合成スコアを送信。 | クライアント送信値の信頼は前提にしない。 |
| 永続成長 | なし。すべて毎プレイ初期化。 | ランキング公平性のため、ショップ・アンロック等を追加しない。 |

## 3. 画面遷移とプレイヤー体験

```text
ホーム
  → 名前入力
  → 3・2・1・GO
  → ゲーム (30ウェーブ)
  → 結果 + 自動スコア送信 + ランキング
```

| 画面 | 主なDOM ID | 役割 | 変更時の注意 |
|---|---|---|---|
| ホーム | `screen-home` | タイトル、開始、ルール、共有、実験場導線。 | 情報を増やしすぎない。中心メッセージは「倒す・拾う・30波」。 |
| 名前入力 | `screen-name`, `player-name-input` | ランキング名を必須入力しlocalStorageへ保存。 | 空欄開始を許可しない。日本語・絵文字・10文字上限を確認。 |
| カウントダウン | `screen-countdown` | 開始前の不意打ちを防ぐ。 | カウント中に敵・弾・タイマーを進めない。 |
| ゲーム | `screen-game`, `game-canvas` | Canvas描画 + 固定HUD。 | 画面スクロール、ズーム、長押しをプレイ中だけ抑制する。 |
| リザルト | `screen-result`, `ranking-list` | 結果、送信状態、再挑戦、下部ランキング。 | 合成された内部スコアを画面に出さない。 |

## 4. `index.html` の実装地図

| セクション | 主な関数・定数 | 責務 | 改修時に確認する依存 |
|---|---|---|---|
| 定数 | `UPGRADES`, `EXP_TABLE`, `ENEMY_TYPES`, `BOSS_TABLE` | バランス値、上限、スコア、敵・ボスの定義。 | バランスは単一項目でなく、DPS・TTK・ドロップとセットで再計測。 |
| 画面・入力 | `showScreen`, `pointerToLogic`, `onPointer*` | 画面遷移、座標変換、タッチ抑制。 | CSSの`touch-action`とJSの`preventDefault`を同時に保つ。 |
| 状態 | `gameState`, `player`, `enemies`, `bullets`, `enemyBullets`, `loots` | 1プレイの状態と動的オブジェクト配列。 | リトライ時にすべてリセットされること。 |
| ループ | `gameLoop`, `update`, `checkCollisions`, `draw` | `requestAnimationFrame`で更新→衝突→描画。 | `delta`上限0.05秒と、フレーム依存ロジックを区別する。 |
| 敵・波 | `getWaveConfig`, `spawnEnemy`, `spawnBoss`, `updateWave` | 30波の出現予約、敵・ボス生成、波クリア。 | 出現数・発射頻度・HP・逃走処理の相互作用を測定する。 |
| 成長 | `spawnLoot`, `collectLoot`, `addExp`, `rollUpgrade`, `applyUpgrade` | 戦利品、経験値、ランダム強化。 | この箇所が公平性の主要リスク。 |
| 結果・ランキング | `buildRankingScore`, `parseRankingScore`, `submitScore`, `fetchRanking` | 結果表示、合成値、Supabase RPC。 | クライアント側の二重送信防止と、サーバー側の値域検証を分けて考える。 |

## 5. 重要な実装値（2026-08-16時点）

| 分類 | 値 | 意味・影響 |
|---|---:|---|
| 初期耐久 | 3 | シールドがない被弾は耐久を1減らす。 |
| 被弾無敵 | 1.2秒 | 連続被弾による即死防止。 |
| 基礎発射間隔 | 0.40秒 | 基礎DPSは2.5発/秒。 |
| 連射強化 | 1段階ごとに間隔×0.85、最大4 | 高火力ビルドとのDPS差を拡大する。 |
| 弾数 | 初期1、最大4 | 火力と横方向の当てやすさを同時に増やす。 |
| 回収範囲 | 初期60、最大150 | 体感生存性・成長速度に大きく効く。 |
| 当たり判定半径 | 初期14、縮小は最大2 | 回避性能に効くが、現在はランダム。 |
| 最大レベル | 12 | Lv.12以後、戦利品は経験値でなくスコアへ変換。 |
| ボスHP | W5=60、W10=110、W15=170、W20=240、W25=290、W30=340 | TTK監査の基準。 |
| 敵弾上限 | 160 | 超過時に古い弾を消す現仕様はバランス上の問題。 |

## 6. ランキングの構造

ランキング比較用の内部値は次式である。

```text
ranking_score = progress × 10,000,000 + display_score
```

`progress` は1〜30の到達ウェーブ、30波クリアは31である。表示時は必ず進行度と表示用スコアへ復元し、内部数値を出さない。表示用スコアは9,999,999でクランプ済みである。

> **重要**: この形式は並び順を守るためのエンコードであり、不正送信を防ぐ署名ではない。クライアントが`p_score`を自由に組み立てられる限り、サーバー側の検証なしに競技順位を信用してはいけない。
