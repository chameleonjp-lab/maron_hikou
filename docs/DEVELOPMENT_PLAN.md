## 2. アーキテクチャ設計(index.html 内部構成)

1ファイル内を以下のセクションに分けて実装する。

```
<head>
  meta viewport(user-scalable=no, viewport-fit=cover)
  <style> 全CSS(画面別クラス、タッチ抑止、セーフエリア対応)
<body>
  #screen-home      ホーム画面(DOM)
  #screen-name      名前入力画面(DOM)
  #screen-countdown カウントダウン(DOM オーバーレイ)
  #screen-game      ゲーム画面(Canvas + 上部HUDはDOM)
  #screen-result    結果画面(DOM、下部にランキング)
  <script>
    [A] 定数・設定値(スコア表、強化定義、ウェーブテーブル)
    [B] 画面遷移マネージャ(showScreen)
    [C] 入力処理(touch/pointer、スクロール抑止)
    [D] ゲームステート(player, enemies[], bullets[], enemyBullets[], loots[])
    [E] ゲームループ(requestAnimationFrame、更新→衝突→描画)
    [F] ウェーブ・敵生成(30波テーブル、5波ごとボス)
    [G] 戦利品・経験値・レベルアップ・強化抽選
    [H] スコア・結果集計
    [I] Supabase 連携(submit_score RPC、ランキング取得・表示)
    [J] シェア(Web Share API / クリップボード)
```

### 設計上の決定事項

- 描画は Canvas、HUD(ウェーブ/スコア/Lv/耐久/シールド/リタイア)は DOM 固定表示。
- 内部解像度は論理座標(例: 幅400固定)で持ち、devicePixelRatio に応じてスケール。iPhone SE(375×667)基準。
- 操作は Pointer Events で統一(touch/mouse 両対応)。機体は指の少し上(約60〜80px)に追従。
- 衝突判定は円判定で統一(プレイヤー被弾判定は小さめ、戦利品回収判定は大きめ)。
- `ranking_score = progress * 10_000_000 + displayScore`。progress: 到達ウェーブ(1〜30)、30波クリアは 31。表示時は `Math.floor(s/1e7)` と `s % 1e7` で復元。内部値は画面に出さない。
- 送信は結果画面表示時に1回だけ。プレイごとに生成する playId フラグで二重送信を防止。リタイア時は送信しない。
- 表示用スコアは 10,000,000 点でクランプする(合成値の桁あふれ防止。理論最大スコアを試算して余裕を確認する)。

## 3. フェーズ計画

### Phase 0: リポジトリ準備 — メインセッション【完了】

CLAUDE.md、仕様書、本計画書、スキル2種の作成とプッシュ。

### Phase 1: 骨格実装 — Sonnet

- index.html の全画面骨格: ホーム → 名前入力 → カウントダウン → ゲーム(空のCanvas+HUD) → 結果(ダミーデータ)
- 全CSS: 縦画面レイアウト、タッチ抑止(touch-action / user-select / touch-callout)、画面別スクロール制御(ホーム・結果はスクロール可、ゲーム中は完全固定)
- 名前入力: 必須・10文字・localStorage 保存/復元・絵文字許可
- カウントダウン 3→2→1→GO
- リタイアボタン+確認ダイアログ(ゲームはまだ無いので結果画面へ遷移するだけ)
- シェア(紹介文): Web Share API / コピーのフォールバック
- 実験場リンク、ルール説明モーダル

**受け入れ基準**: 375px 幅で横はみ出しなし。全画面遷移が動く。空欄で開始不可。

### Phase 2: ゲームコア — Opus

- ゲームループ(rAF、deltaTime ベース)
- プレイヤー機体: 指追従移動、自動ショット(弾数1〜4の横展開、連射強化、貫通)
- 敵: 小型・中型・大型の3種+移動パターン(直進・横移動・蛇行)、敵弾
- 衝突判定: プレイヤー弾×敵、敵弾×プレイヤー、敵×プレイヤー
- 被弾処理: シールド→耐久、無敵時間、耐久0でゲームオーバー
- 画面外・撃破済みオブジェクトの確実な削除

**受け入れ基準**: 仕様 §14〜16 の数値どおり。配列が無限に増えない。

### Phase 3: 戦利品・成長システム — Opus

- 戦利品ドロップ(🔧/✨/🎁、敵種別ドロップ率)、落下、接近回収、回収範囲強化反映
- 経験値・レベルアップ(上限 Lv.12、以降はスコア加算へ切替)
- 強化抽選: 7種、各上限管理、上限到達分は抽選除外、全上限時はスコアボーナス
- レベルアップ表示・ウェーブ開始表示

**受け入れ基準**: §17〜20 どおり。上限後に同じ強化が当たらない。

### Phase 4: ウェーブ進行・スコア — Opus

- 30波テーブル(§21 の区間設計、難易度カーブ)
- 5/10/15/20/25/30 波のボス(体力・弾幕は段階的に強化)
- スコア(§23 の点数表)、ウェーブ突破ボーナス、30波クリア処理
- 結果集計(到達ウェーブ、スコア、最終Lv、撃破数、戦利品数)

**受け入れ基準**: 1〜30波が順に進み、30波ボス撃破でクリアになる。

### Phase 5: Supabase 連携 — メインセッション(高難度) + Sonnet(表示UI)

- ranking_score 合成・復元の実装と単体検証(メイン)
- submit_score RPC 呼び出し(p_display_name / p_game_slug / p_score / p_client_version)
- 二重送信防止、リタイア時非送信、失敗時の「送信失敗」表示(メイン)
- 結果画面下部ランキング(上位10件、同率順位 1位/1位/3位 方式、横スクロールなし)(Sonnet)
- ベスト更新表示(localStorage に自己ベスト ranking_score を保持)
- 結果シェア文(§29 のフォーマット)

**受け入れ基準**: §24〜27 どおり。内部スコアが画面に出ない。

**⚠️ ブロッカー**: Supabase の URL と anon キーが必要。既存ゲーム(実験場の他ゲーム)と同じ値を流用する想定。ユーザーから提供されるか、既存ゲームの index.html から確認する。

### Phase 6: スマホ最適化・調整 — Sonnet + メイン監査

- iPhone SE(375×667)での全画面レイアウト最終確認(§13)
- セーフエリア(env(safe-area-inset-*))対応
- パフォーマンス: オブジェクト数上限、描画負荷確認(§35)
- 難易度バランス調整(序盤で即死しない、強化不足だと21波以降が厳しい)

### Phase 7: 最終監査・検証 — メインセッション

- `/spec-audit` を実行し §36(不具合一覧)・§37(確認項目)・§39(10大要件)を全件チェック
- Node で擬似実行できるロジック(ranking_score 変換、強化抽選、ウェーブテーブル)は単体テストで検証
- 不合格項目は該当フェーズの担当モデルに差し戻し

### Phase 8: 公開・実験場登録 — 手作業ガイド作成(メイン)

## 5. リスクと対応

| リスク | 対応 |
|---|---|
| Supabase 接続情報が未提供 | Phase 5 開始前にユーザーへ確認。それまで送信部はモック化して進める |
| submit_score の引数仕様が想定と違う | 既存ゲームの実装を取得して照合してから実装する |
| 表示用スコアが 10,000,000 を超える | クランプ実装+理論最大値の試算で防止 |
| iPhone 実機が手元にない | DevTools の 375×667 エミュレーションで代替し、ユーザーに実機確認を依頼 |
| 1ファイルが巨大化しサブエージェント編集が衝突 | フェーズは直列実行(同時に index.html を触らせない) |
| 後半ウェーブの処理落ち | 敵弾・戦利品の同時表示数に上限を設ける |
